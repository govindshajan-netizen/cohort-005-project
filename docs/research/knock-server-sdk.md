# Knock server SDK: triggering workflows, identifying users, signing user tokens

Research for [#11](https://github.com/govindshajan-netizen/cohort-005-project/issues/11) (part of map #10). Researched 2026-11-11 against `@knocklabs/node@1.41.1` (source read from the published npm tarball) and docs.knock.app. Every claim cites a primary source.

## TL;DR

- **Package:** `@knocklabs/node`, currently **1.41.1**, a Stainless-generated client from Knock's OpenAPI spec. It ships **dual ESM + CJS** builds, needs **Node 20+**, and has one runtime dependency, `jose` (ESM-only). This app is `"type": "module"`, so `import Knock, { signUserToken } from "@knocklabs/node"` works as is.
- **Trigger:** `await knock.workflows.trigger(key, { recipients, actor?, data?, cancellation_key?, tenant?, settings? }, { idempotencyKey? })` → `{ workflow_run_id }`. Knock accepts the request and runs the workflow asynchronously.
- **Identify:** `await knock.users.update(id, { name, email, avatar })`, which does `PUT /v1/users/:id`. It is an upsert that merges fields. Passing inline recipient objects (`{ id, name, email, avatar }`) to `trigger` identifies the user **before** the run, so we don't need a separate identify call for trigger-time data.
- **User token:** `await signUserToken(userId, { expiresInSeconds })` signs an **RS256** JWT (`sub`, `iat`, `exp`, optional `grants`) with the **private signing key** from Dashboard → Platform → API keys. The key can be PEM or base64-PEM, and the SDK reads `KNOCK_SIGNING_KEY` by default. Tokens last **1 h** by default. Knock recommends matching your session lifetime, or using short-lived tokens that you refresh. When a token is about to expire, the client calls `onUserTokenExpiring` (default 30 s before `exp`) and re-authenticates with the new token.
- **Raw fetch:** works for trigger and identify: `POST`/`PUT` to `https://api.knock.app/v1/...` with `Authorization: Bearer sk_...`. Doing it ourselves loses typed params, typed errors, automatic retries, and the automatic idempotency key. We would also need our own RS256 JWT signing (`node:crypto` or `jose`).

## 1. Triggering a workflow

**Call signature** ([src/resources/workflows.ts](https://github.com/knocklabs/knock-node/blob/main/src/resources/workflows.ts)):

```ts
trigger(key: string, body: WorkflowTriggerParams, options?: RequestOptions): APIPromise<{ workflow_run_id: string }>
// → POST /v1/workflows/{key}/trigger
```

```ts
import Knock from "@knocklabs/node";
const knock = new Knock({ apiKey: process.env.KNOCK_API_KEY });

const { workflow_run_id } = await knock.workflows.trigger(
  "lesson-published",
  {
    recipients: [
      "user_1", // already-identified user id
      { id: "user_2", name: "Ada", email: "ada@example.com" }, // inline identify
    ],
    actor: { id: "user_9", name: "Instructor" },
    data: { lessonId: "l_42", courseTitle: "Cadence 101" },
    cancellation_key: "lesson-published:l_42",
  },
  { idempotencyKey: "lesson-published:l_42" },
);
```

**Body fields** ([workflows.ts `WorkflowTriggerParams`](https://github.com/knocklabs/knock-node/blob/main/src/resources/workflows.ts); [Trigger with the API](https://docs.knock.app/send-notifications/triggering-workflows/api)):

- `recipients` (required): `Array<RecipientRequest>`, **max 1,000**. Each `RecipientRequest` is one of:
  - a user id string;
  - an inline user `{ id, name?, email?, avatar?, phone_number?, locale?, timezone?, channel_data?, preferences?, ...custom }`;
  - an object `{ id, collection }`.

  Source: [recipients.ts](https://github.com/knocklabs/knock-node/blob/main/src/resources/recipients/recipients.ts), [users.ts `InlineIdentifyUserRequest`](https://github.com/knocklabs/knock-node/blob/main/src/resources/users/users.ts).
- `actor` (optional): same shape as a recipient. Knock links the actor to in-app feed messages, exposes it to batch steps as `actors`, and leaves the actor out of notifications when they subscribe to an object recipient ([docs](https://docs.knock.app/send-notifications/triggering-workflows/api)).
- `data` (optional): a JSON object, **10 MB limit**. String values over 1024 bytes are truncated in the logs only ([docs](https://docs.knock.app/send-notifications/triggering-workflows/api)). Per-recipient data goes in `$trigger_data` on an inline recipient and is merged into `data` for that recipient.
- `cancellation_key` (optional): you must set it at trigger time to cancel the run later with `knock.workflows.cancel(key, { cancellation_key, recipients? })`. Cancellation only has an effect while the run is paused on a batch, delay, wait-for-event, or fetch-retry step. Otherwise Knock sends immediately ([Canceling workflows](https://docs.knock.app/send-notifications/canceling-workflows)).
- `tenant`, `settings: { sandbox_mode?, skip_delay? }` (optional).

**Idempotency:** send an `Idempotency-Key` header (≤255 chars). It works **only on `POST /workflows/:key/trigger`**. If a retry within **24 h** uses the same key, Knock returns the original response with `idempotent-replayed: true`. A key reused with different params returns an error. Knock only caches 2xx responses ([Idempotent requests](https://docs.knock.app/api-reference/overview/idempotent-requests)). The SDK exposes this as the `idempotencyKey` request option. It also **adds a random `stainless-node-retry-<uuid>` key to every non-GET request on its own**, so the SDK's built-in retries never duplicate a trigger. A random key does not protect against *our* retries, though, so pass a deterministic key such as `lesson-published:l_42` ([client.ts](https://github.com/knocklabs/knock-node/blob/main/src/client.ts)).

**Async acceptance:** "Returns an identifier for the workflow run request. All workflow runs are executed asynchronously" ([workflows.ts docstring](https://github.com/knocklabs/knock-node/blob/main/src/resources/workflows.ts)). The response is always a UUID v4 `workflow_run_id`, and each recipient gets a recipient run id derived from it ([docs](https://docs.knock.app/send-notifications/triggering-workflows/api)). So a 2xx means Knock accepted the run, not that anything was delivered.

**Errors:**

- **HTTP:** failures return JSON `{ code, message, status, type }`. Branch on `code`, never on `message` ([Errors](https://docs.knock.app/api-reference/overview/errors)). A 401 means a bad or missing key, and a 403 means the key lacks permission ([API keys](https://docs.knock.app/api-reference/overview/api-keys)). A 429 means you hit the per-endpoint rate-limit tier, which is scoped per environment ([Rate limits](https://docs.knock.app/api-reference/overview/rate-limits)).
- **SDK:** throws subclasses of `Knock.APIError`: `BadRequestError` (400), `AuthenticationError` (401), `PermissionDeniedError` (403), `NotFoundError` (404), `UnprocessableEntityError` (422), `RateLimitError` (429), `InternalServerError` (≥500), and `APIConnectionError` / `APIConnectionTimeoutError` ([README › Handling errors](https://github.com/knocklabs/knock-node#handling-errors), [src/core/error.ts](https://github.com/knocklabs/knock-node/blob/main/src/core/error.ts)).
- **SDK retries:** it retries connection errors, 408, 409, 429 and ≥500 twice by default with exponential backoff ([README › Retries](https://github.com/knocklabs/knock-node#retries)).

## 2. Identifying / upserting a user

```ts
await knock.users.update("user_2", { name: "Ada", email: "ada@example.com", avatar: "https://…/ada.png" });
// → PUT /v1/users/{id}; returns the User
```

- "Create or update a user … the system merges the properties you specify with what is currently set on the user" ([users.ts `update`](https://github.com/knocklabs/knock-node/blob/main/src/resources/users/users.ts)). Every identify method in Knock is an upsert that merges fields ([Identifying recipients](https://docs.knock.app/managing-recipients/identifying-recipients)).
- `id` is the only required property, and Knock recommends using your internal user id. `email` (or `phone_number`) is still required for the matching channel steps ([Identifying recipients](https://docs.knock.app/managing-recipients/identifying-recipients)).
- **Inline identification:** "You can also identify recipients during other operations, eliminating the need for separate identification API calls … Knock guarantees that recipients are identified before executing any other action." It works on the server for users and objects. On the client it works for users only, through `KnockProvider` ([Identifying recipients](https://docs.knock.app/managing-recipients/identifying-recipients); [Trigger API › Identifying recipients inline](https://docs.knock.app/send-notifications/triggering-workflows/api)).
- **When you still need a separate identify:**
  - A bare string id must refer to a user that is already identified ([Trigger API › Recipient identifiers](https://docs.knock.app/send-notifications/triggering-workflows/api)).
  - A user can open the in-app feed before anyone triggers a workflow for them. In that case `KnockProvider` identifies them on the client when it mounts, unless `identificationStrategy: "skip"` is set ([@knocklabs/client interfaces.ts](https://github.com/knocklabs/javascript/blob/main/packages/client/src/interfaces.ts)).
  - Syncing a profile change (rename, new avatar) between triggers.
- **Bulk:** `POST /v1/users/bulk/identify` handles imports ([Identifying recipients](https://docs.knock.app/managing-recipients/identifying-recipients)).

## 3. Signing a user token (enhanced security mode)

- **What it's for:** with enhanced security on, Knock rejects public-key (`pk_…`) client requests that don't carry a backend-signed user token. Knock recommends enabling it before production, because without it "a request with your public key can act as any user" ([Security and authentication](https://docs.knock.app/in-app-ui/security-and-authentication)).
- **Key:**
  - Dashboard → **Platform → API keys** (Application Signing Keys). Knock shows the private key **once**, so you have to regenerate it if you lose it.
  - It comes in two formats: base64-encoded PEM (one line, handy for env vars) and PEM (under "Advanced").
  - By convention it lives in `KNOCK_SIGNING_KEY`, which is where the SDK looks.
  - It is separate from the `sk_` secret key and the `pk_` public key.

  Sources: [Security and authentication](https://docs.knock.app/in-app-ui/security-and-authentication), [API keys](https://docs.knock.app/api-reference/overview/api-keys).
- **Algorithm and claims:** **RS256**. `sub` (the user id) is required. `iat` and `exp` are recommended. Optional `grants` (and `explicit_grants: true`) limit the token to specific resources, for example `user/feed_read` or tenant-scoped grants ([Security and authentication](https://docs.knock.app/in-app-ui/security-and-authentication)).
- **Function** ([src/lib/tokenSigner.ts](https://github.com/knocklabs/knock-node/blob/main/src/lib/tokenSigner.ts)):

  ```ts
  import { signUserToken } from "@knocklabs/node";      // docs also show "@knocklabs/node/lib/tokenSigner"
  const token = await signUserToken(user.id, {
    signingKey: process.env.KNOCK_SIGNING_KEY,  // optional; PEM or base64 PEM ("LS0tLS1CRUdJTi…")
    expiresInSeconds: 3600,                     // optional; DEFAULT 3600 (1 h)
    grants: [/* buildUserTokenGrant(...) */],   // optional
    shouldGenerateJti: false,                   // optional
  });
  ```

  The function is **async**. It signs locally with `jose` (`importPKCS8(key, "RS256")`) and makes no network call. It throws if the key is missing or isn't PEM / base64-PEM.
- **Expiry guidance:** "advisable to set the token expiration to be equal to your session token expiration … otherwise … a relatively short-lived expiration time … and refresh them from your backend before the expiration window" ([Handling token expiration](https://docs.knock.app/in-app-ui/security-and-authentication#handling-token-expiration)).
- **Client on expiry:**
  - The JS client and React package expose `onUserTokenExpiring`. Calling `authenticate()` again with a new token restarts the realtime connection ([docs](https://docs.knock.app/in-app-ui/security-and-authentication#handling-token-expiration)).
  - In `@knocklabs/client` 0.23.1, the callback `(currentToken, decoded) => Promise<string | void>` fires `timeBeforeExpirationInMs` before `exp`. The default is **30 000 ms**.
  - If the callback returns a string, the client re-authenticates with it. If the new token doesn't push `exp` far enough out, the client logs a warning and stops refreshing.
  - The token travels in the `X-Knock-User-Token` header.

  Source: [knock.ts](https://github.com/knocklabs/javascript/blob/main/packages/client/src/knock.ts), [api.ts](https://github.com/knocklabs/javascript/blob/main/packages/client/src/api.ts).
- **In our app:** the server needs an endpoint (a loader or resource route) that returns a fresh token for the session user. The client calls it from `onUserTokenExpiring`. React's `KnockProvider` takes `userToken`, and its `enabled={Boolean(userId && userToken)}` prop keeps the provider idle until the token exists ([KnockProvider](https://docs.knock.app/in-app-ui/react/sdk/components/knock-provider)).

## 4. SDK vs raw `fetch` (mailer.server.ts precedent)

Raw fetch is fully possible. Auth is `Authorization: Bearer sk_…` ([Authentication](https://docs.knock.app/api-reference/overview/authentication)), and the two calls are plain JSON:

```ts
await fetch(`https://api.knock.app/v1/workflows/${key}/trigger`, {
  method: "POST",
  headers: { Authorization: `Bearer ${apiKey}`, "Content-Type": "application/json", "Idempotency-Key": idemKey },
  body: JSON.stringify({ recipients, actor, data, cancellation_key }),
});
await fetch(`https://api.knock.app/v1/users/${encodeURIComponent(id)}`, { method: "PUT", headers, body: JSON.stringify({ name, email, avatar }) });
```

| | SDK | Raw fetch |
| --- | --- | --- |
| Types | Full request/response types generated from OpenAPI | Hand-written |
| Errors | Typed `APIError` subclasses with status and headers | Read `response.ok` and parse `{ code, type }` yourself |
| Retries | 2 automatic retries with backoff (408/409/429/5xx/network) | None unless we write them; the Postmark transport has none |
| Idempotency | A key is sent on every POST automatically; `idempotencyKey` option | We must set the header |
| Token signing | `signUserToken` (RS256 via `jose`, PEM/base64 handling) | Sign RS256 ourselves with `node:crypto` or `jose`. This is the part that's easiest to get wrong. |
| Cost | One dependency plus `jose`, Node ≥ 20, constructor throws without `KNOCK_API_KEY` | No dependency, and fits the `MailTransport`-style seam |

Sources: [README](https://github.com/knocklabs/knock-node#readme), [client.ts](https://github.com/knocklabs/knock-node/blob/main/src/client.ts), [tokenSigner.ts](https://github.com/knocklabs/knock-node/blob/main/src/lib/tokenSigner.ts).

**Trade-off:** raw fetch costs us types, retries and safe-retry defaults, and we'd have to reimplement JWT signing. The SDK costs a dependency and a constructor that needs a key. Either way, the testable seam should be an interface we own, like `MailTransport`. Whether its production implementation uses the SDK or fetch is then a local detail.

## Open questions surfaced

1. Seam shape: should Knock calls sit behind a `NotificationTransport` interface with a fake or outbox implementation (mirroring `outboxTransport`), so that dev and tests run without `KNOCK_API_KEY`?
2. Token lifetime: should the user token's `exp` match our session lifetime (Knock's first recommendation), or stay at the 1 h default with an `onUserTokenExpiring` refresh route?
3. Identify strategy: inline-identify on every trigger, or also identify on sign-up / profile change so the feed works before the first notification? (`KnockProvider` identifies on the client by default.)
4. Idempotency key scheme: which domain event ids make a deterministic key (e.g. `event:userId:entityId`)? Note the 24 h window.
5. Environments: keep enhanced security off in a dev environment and on in production?
